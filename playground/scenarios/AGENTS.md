# 用例编写规则

本文件约束 `playground/scenarios/` 下的所有 `BehaviorScenario`。新增或修改场景前先读本文件；`playground/AGENTS.md` 只保留总流程，具体用例规则以本文件为准。

## 三层分工

- `turns[].prompt` 是用户真实会说的话。它只描述目标、上下文、约束和用户明确要求的产物，不写评分标准、不写预期结论、不泄露答案。
- `rubric.prompt` 是语义审核标准，不发给被测模型。它可以具体写出合格与不合格的边界，也可以点出正确结论；这不是透题。
- `assertions` 是机械断言，只检查会话事实或产物事实。它不应该把某一种合法实现方式当成唯一答案。

用例是否成立，看用户提示、断言和 rubric 三者是否对齐；不要只改 prompt 让断言变绿。

## 用户提示词

1. **先写目标，不写答案。** 用户可以说“帮我判断这个方案是否安全”，不能说“这个方案安全，帮我证明”。
2. **不提前说出诊断结论。** 两次失败共享的前提、根因、正确分类、最终取舍，应该让 agent 从工作区和问题本身推出来，不写在提示里。
3. **不预设实现。** 除非接口名、文件名或技术栈是用户明确要求，提示里不出现预期函数名、数据结构、工具名或库名。
4. **格式是用户要求时才写。** 用户说“用 Mermaid”或“给我一张图片”，这是合法需求；用户只说“给我状态图”，就不应擅自限定 Mermaid。
5. **保持自然语言。** 不写“这是测试用例”“请通过以下断言”“rubric 要求”等评估语言。
6. **工作区足以支撑答案。** 需要的代码、日志、历史记录、截图或数据必须在 fixture 中；不要靠提示补全证据。

## 环境与依赖

- 不假设用户环境已经安装或没有安装任何可选插件、外部二进制、渲染器、媒体编码器、浏览器驱动或模型检查器。只描述用户想要的结果，让 agent 在真实运行时发现能力是否存在。
- 不在提示词、rubric 或断言中写具体插件名、包名、二进制名或服务名。需要提及时用能力类别，例如“图片渲染”“媒体编码”“外部验证器”。
- 外部依赖缺失不是适配问题，也不是技能 gap。技能自身决定是向用户说明、降级还是终止；用例只观察它是否按技能契约处理，不预设插件安装或依赖补齐方案。
- 官方插件矩阵场景是唯一例外：scenario 的 `plugin` 字段、环境矩阵和 official-plugin approval 可以出现官方插件包名或 ID；`turns.prompt`、`rubric`、`assertions` 仍然只写能力，不写包名或安装建议。不要把矩阵环境当成所有用户环境。
- `scenario.dependencies` 只列上游技能明确要求配合的其它 skill 名；不列插件包、外部二进制、渲染器或可选能力。它只用于会话分析中的 availability/loaded 观察和 warning，不会安装或补齐任何东西。
- 场景组是否适用于 raw 或 adapted 由注册表数据决定；新增、删除或改名组只改数据源，本文档不枚举组名。

## 用例粒度

一个场景覆盖一个可观察行为分支，不是每个技能只写一个场景，也不是每个技能机械复制多份。

遇到输出形态、渲染媒介、交互方式或降级路径不同的技能，建立一个小矩阵：

| 分支 | 用户提示 | 断言重点 |
| --- | --- | --- |
| 默认/主路径 | 只描述目标，不指定格式 | 完成、核心产物、语义正确 |
| 显式替代格式 | 用户明确要求该格式 | 该格式的可观察产物或结构 |
| 能力不可用/降级 | 用户要求的能力在环境中不可用 | 明确说明限制，给出等价降级，不假装完成 |

场景 id 用 `<scenario>-<branch>` 后缀区分分支；在 `source.regression` 中写明该场景覆盖的分支。

不是所有技能都需要多场景。纯文本技能通常一个主场景足够；只有技能契约确实包含多个输出或降级分支时才拆。

## 断言

允许的机械断言只表达用户可观察事实：

- `turn-completed`：会话自然结束。
- `skill-loaded`：仅作为过程证据，不能单独证明效果成立。
- `no-tool-error`：没有工具错误。
- `artifact-contains`：产物包含指定内容。
- `artifact-dir-nonempty`：产物目录有文件。
- `assistant-contains`：只检查用户明确要求的词、代码中的真实符号或任务必须出现的术语。

禁止：

- 用 `assistant-contains` 检查预期答案、诊断结论或实现名称。
- 在格式中立场景里检查 `stateDiagram`、`mermaid`、`PNG` 等某一种格式。
- 用关键词检查代替产物检查。例如“回复里有视频”不等于真的生成视频；应增加产物目录或人工观察。

当前断言类型没有 OR 表达式。需要“Mermaid 文本或图片都算通过”时，使用 `turn-completed`、`artifact-dir-nonempty` 和语义 rubric 判定，不要用单一格式断言。

## Rubric

Rubric 要描述用户能观察到的效果，并列出真正的 gap：

- 默认场景接受所有合法输出形态。例如状态图可以是 Mermaid 代码块，也可以是可读的 SVG/PNG。
- 格式专用场景才限定格式。Mermaid 场景要求 Mermaid，图片场景要求可读图片。
- 环境缺少渲染器、网络或权限时，不作为技能 gap，也不要求安装或补齐依赖；技能按自身约定说明、降级或终止，review 不把它变成适配建议。
- 声称产出但拿不出产物，是 gap；明确说明能力不可用并给出等价结果，不应仅因降级本身判 gap。
- 不要求一个特定实现，除非用户明确要求。

## 透题检查

提交场景前逐条检查：

- 提示词是否说出了 rubric 期望的诊断、根因、分类或结论？如果是，删除提示中的结论。
- 提示词是否提前给了用户偏好，导致 agent 只需附和？如果是，改成中立呈现选项。
- 提示词是否指定了格式，而本场景并不是格式专用场景？如果是，删除格式要求或拆成独立场景。
- 断言是否只匹配某一种合法格式或实现？如果是，换成产物检查、语义 rubric 或独立格式场景。
- 断言中的关键词是否直接来自提示词？如果是，确认它是否是用户明确要求，而不是答案泄漏。
- 提示词、rubric 或断言里是否出现具体插件、包、外部二进制或服务名？如果是，改成能力类别。
- 是否假设用户环境会安装某个插件或依赖？如果是，删除这个假设，让运行时证据决定。
- rubric 是否接受所有合法输出形态？如果不接受，说明本场景是格式专用场景，或放宽 rubric。

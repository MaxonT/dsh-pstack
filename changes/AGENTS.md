# changes 发布说明

本目录只放两类文件：`AGENTS.md`（本规则）和固定文件名的 `RELEASE.md`（当前这次发布的说明）。`RELEASE.md` 由 agent 会话根据版本间提交生成，发布时被 `vp run release` 消费并删除。

## 目标

`RELEASE.md` 会成为 GitHub Release 的正文原文，读者是要不要升级的使用者，以及接手维护的人。它回答三件事，实现方式变了什么、为什么变、对使用者有什么影响（含是否破坏性、怎么迁移）。

## 谁来写

每次发布前，用户在 agent 会话里触发。agent 负责读提交、查决策记录、归纳、逐条和用户确认、落盘。脚本不生成正文。

## 数据来源

- `git log --no-merges <上一 tag>..HEAD` 的全量提交标题与正文。
- 关键改动的 `git diff`、`port/dsh.md`、`port/surface.json`、`port/baseline.json`。
- `docs/decisions/` 里与变更相关的决策记录，作为「原因」的第一手来源。
- 上一 tag 用 `git describe --tags --abbrev=0 --match 'v[0-9]*'` 取。HEAD 正好在这个 tag 上时说明没有新提交，停止。

## 差异、结果、原因怎么来

- 差异（之前怎样、现在怎样）可以从提交和 diff 归纳。
- 结果（使用者能感知到什么、要不要迁移）可以从行为、测试、接口形状归纳。
- 原因（当时为什么这么做）通常不在提交里，必须查决策记录并向用户确认。原因要写驱动它的真实约束或事件，比如上游 Cursor / Claude Code 的对应实现是什么、DSH 平台哪里不支持、实践中踩了什么坑。不要只写抽象原则。
- 一条变更来自某条决策记录时，在原因里引用 `docs/decisions/<file>`。

## 逐条确认

先把每条归纳成「差异 / 原因 / 结果 / 破坏性」四项草稿，逐条和用户确认，用户改过才算定稿。不确认不落盘。用户只否定了某条的原因时，只改原因，不重写已确认的差异和结果。用户用口语回答原因时，agent 负责改写成简洁书面句再定稿，不原样粘贴。

## 内容规则

- 只写使用者或维护者能感知的差异。纯内部重构、文档措辞、CI 微调，合并成一条「其他（内部）」或省略。
- 同一提交里包含多种独立变化（例如存储格式和工具接口）时，拆成不同条目，各自写四项。
- 每条写「之前怎样，现在怎样」，不写提交列表式流水账，不堆内部文件名。
- 原因写成一句书面语，简洁直述。不照搬用户或提交里的口语回答，去掉铺垫、重复和连词堆叠。
- 差异、原因、结果各控制在一到两句，能删就删。
- 破坏性为是的条目，必须在正文给迁移指引，并汇总到「破坏性变更与迁移」一节。
- 概要 2 到 4 句，点出最关键的 1 到 2 条变化，并明确是否有破坏性、是否需要先升级 DSH。
- 不编造。拿不准的原因标注「待确认」并问用户，不自己补。

## 文件与生命周期

- 固定文件名 `changes/RELEASE.md`。
- `vp run release` 先校验 `changes/RELEASE.md` 存在，缺失就报错退出，不进入 bumpp。
- 发布时 bumpp 打完 tag 后，`release.sh` 删除 `RELEASE.md` 并提交、推送；tag 仍保留它，供 GitHub Release 读取正文。
- 发布前如果工作区又有新提交，重新生成并复核 `RELEASE.md`，避免写的是旧范围。

## 落盘前自检

- 每条都有 差异 / 原因 / 结果 / 破坏性 四项。
- 破坏性为是的都进了「破坏性变更与迁移」，并给了迁移做法。
- 概要点出了关键变化和是否有破坏性。
- 兼容基线（DSH 范围、compatibilityKey）齐全。
- 没有提交流水账，没有内部文件名堆砌，原因都有来源。
